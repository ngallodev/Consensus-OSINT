## Excluded and directly inspected scope

Codebase Memory excludes `consensus_osint/vendor/` and reports 34 ignored template assets. `file` inventoried all listed assets; the two unusable templates were searched directly for script/network references. They contain inline scripts and generated external links; no `fetch`/XHR reference was found, and the graph template declares CSP `connect-src 'none'` (`consensus_osint/templates/graph.html.j2:1-16`; `report.html.j2:217-229`). This does not verify rendered output, browser behavior, or the destination of generated links. The vendor tree contains multiple family licenses and numerous independent provider clients; direct searches were used to identify representative call sites, not to certify every provider. Phase 0 included no packet capture, namespace/firewall, proxy, DNS, HTTP, browser, or live-provider experiment.

## Phase 1 questions

1. Inventory every client/resolver/socket/subprocess across core, adapters, vendored families and provider modules; identify reachable paths from each CLI command.
2. Prove allowed proxy traffic and detect direct TCP/UDP/DNS with local fake endpoints and restricted egress.
3. Test explicit Tor remote DNS, absent/unhealthy route failure, redirects, retries, curl_cffi, user-scanner hooks, browser, FlareSolverr and update routes.
4. Define a narrow approved module set only after each enabled path passes; report exact observations rather than inferring from flags.

## Phase 1 audit findings

The scoped search covered `consensus_osint/core`, `adapters`, and `vendor` for HTTPX, requests, urllib, aiohttp, curl_cffi, DNS resolvers, sockets, subprocesses and browser/solver entrypoints. It is not a complete call graph of every vendored provider. The shared HTTPX client retains `trust_env=True` in standalone mode and sets it false only under `OSINT_REQUIRE_PROXY=1`; loopback fixtures verified ambient `HTTP_PROXY` in standalone mode and strict explicit-proxy precedence over a conflicting ambient proxy. This also preserves HTTPX's standalone CA environment handling, but CA bundle loading was not separately exercised. Standalone AI and vendor transports were not changed. Tor's shared-client default is `socks5h://127.0.0.1:9050`. An isolated fake SOCKS proxy received the hostname in SOCKS5 domain-name form, and no local UDP/53 packet was observed. Strict mode blocks missing shared-client routes and makes network-status telemetry skip direct/system-proxy probes. These guards do not cover independent clients.

No phase-1 route is approved for suite use. Static inspection cannot establish whether a request was emitted or blocked.

`tools/egress-harness/run.py` ran under `unshare --user --map-root-user --net`. It confirmed proxy routing, Tor remote-DNS proxying, missing/unavailable route behavior, and packet capture. nftables rules drop all non-loopback output; a dummy sink and documentation-range routes let the harness confirm denied TCP and DNS/UDP counters without a physical interface or default route. `nft` is at `/usr/sbin/nft`; `tcpdump` is installed (capture uses AF_PACKET directly); `iptables` is unavailable. The dnspython resolver, vendor, AI, browser, solver, updater and other independent clients remain unverified.
